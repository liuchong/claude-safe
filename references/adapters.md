# 本机 VPN、虚拟网卡、分流和浏览器

## 1. 选择接管方式

1. 检查当前网络软件和实际内核。优先复用正在工作的配置；无客户端时按 [软件准备](software.md) 安装一套。
2. 有 Mihomo/Clash Verge Rev 时走下一节固定节点分流，适合既有其他产品分流。已有 Shadowrocket/Surge/sing-box 时只用其原生节点格式，不把 Mihomo JSON/YAML 整段导入。
3. 只需要 Claude Code 且已有 HTTP/HTTPS 代理时，可对该进程显式设置代理环境，不强制全机 TUN。浏览器和 Desktop 是否使用系统代理要独立实测；一个 shell 的环境变量不代表所有应用。
4. 原生 WireGuard App 的全隧道会影响整机出口。只有用户明确允许整机路由变化时才使用；否则使用支持按域名分流的客户端，不偷偷将整机默认路由改到 VPS。

## 2. Mihomo 持久合并

1. 在客户端“配置/Profiles”找到实际启用条目，再找到该条目的持久覆写、合并或脚本入口。复制本轮必要字段到受限备份；不要编辑重启即消失的内核运行文件。
2. 新 VPS 节点用 network_plan.py 的 client 分支生成，现有节点则引用原来的真实名称。检查是否已有同名 Claude-Safe / Claude-Safe-WG，避免覆盖别人配置；存在不同用途时只给本轮节点改明确的新名字并同步引用。
3. 将生成的 proxies 记录追加为新节点，proxy-groups 追加为只含该节点的 select。rules 放在可能抢先命中的泛用规则和 MATCH 前面；规则集中的顺序有语义，不能简单放末尾。
4. 固定组不得包含 DIRECT、自动 fallback、url-test 或另一可变节点组；只有一个明确节点。目标故障时应失败，不自动切换国家或直连。
5. 本项目给出 JSON；JSON 也是 YAML 的子集，但它是合并片段，不是完整订阅配置。使用客户端持久合并，或在宿主已有 YAML 解析器中结构化合并；不要用正则重写整份 YAML，不覆盖其他节点和规则。
6. 已有订阅更新时，配置依然按“订阅→持久覆写→最终完整配置”生成。加载前导出这一次最终配置到受限临时文件，不在聊天打印其中密钥。
7. 找到该客户端实际使用的 Mihomo 内核二进制，用 `'<内核>' -t -f '<完整配置>'` 校验，设 15 秒截止。通过后在客户端加载/刷新；报未知字段先核对当前内核版本，不删除必要语义来凑通过。
8. 从本机控制器读取 version、configs、proxies、rules、connections 的必要字段；只用已绑定回环地址的现有接口，认证通过受限请求配置传入，不放 URL、日志和命令参数。没有控制器时用客户端连接面板，不为自动化暴露公网控制端口。

## 3. DNS

1. 看清当前 DNS 模式及用户的局域网/公司域名。保留已有可用 nameserver、局域网域名和私有解析，目标域名单独指定策略，不全机乱换 DNS。
2. 对上面 WireGuard 节点，endpoint 已用 IPv4，避免解析节点本身又依赖节点。节点的 remote-dns-resolve 与 dns 已由生成器填写；这不等于系统/浏览器所有 DNS 自动进入隧道。
3. Mihomo 开启内置 DNS 时，把以下片段合入现有 dns.nameserver-policy；若现有同名键不同先查用途，不能覆盖全局 nameserver-policy：

```yaml
dns:
  nameserver-policy:
    '+.claude.ai': ['1.1.1.1#Claude-Safe']
    '+.claude.com': ['1.1.1.1#Claude-Safe']
    '+.anthropic.com': ['1.1.1.1#Claude-Safe']
```

4. 如果节点使用域名，proxy-server-nameserver 必须能不经过尚未建立的节点解析它；选择现有已验证解析器，不能制造“必须先连隧道才能解析隧道”的循环。
5. 不为了修目标请求就切换全局 fake-ip/redir-host 或清空所有 fallback。先检查目标 DNS 实际命中、DNS 请求出站和本次应用连接。
6. 浏览器开启独立安全 DNS 时，系统 DNS 改动可能不覆盖它。选择让该浏览器使用现有受控解析或将其安全 DNS 实际流量纳入已验证策略，读回设置；不以系统 nslookup 正常证明浏览器正常。
7. IPv6 不受当前节点支持时检查是否仍有目标 AAAA/IPv6 连接绕行；在客户端/目标应用范围内禁用目标 IPv6 或使用支持 IPv6 的节点。全机禁 IPv6 仅在明确授权且确有必要时做，并复验局域网和已有业务。

## 4. TUN 与虚拟网卡

1. TUN 是接管方式，不是目标出口。先查看现有 VPN、虚拟网卡和默认路由，保存要修改部分，不删除其他工具网卡。
2. 在支持服务模式的客户端先安装/启用其正式服务，再启用 TUN。macOS/Windows 网络扩展、驱动、UAC 或系统 VPN 允许框由本人确认。
3. 对有完整现行配置的新 Mihomo TUN，基础字段是 enable、stack、auto-route、auto-detect-interface 和 dns-hijack；保留已有成熟值，仅缺失时采用以下起点：

```yaml
tun:
  enable: true
  stack: mixed
  auto-route: true
  auto-detect-interface: true
  dns-hijack:
    - any:53
```

4. 原生内核校验通过才加载。启动后查新增的实际接口和路由，确认 SSH 管理连接、局域网及原有直连用途仍可用；启动图标亮起不算接管成功。
5. 系统代理用于会遵循它的应用；TUN 接管更多流量，但浏览器 WebRTC、IPv6、DNS 和进程专用代理仍分别核验。不把二者开关等同于“全流量已安全”。
6. 两个 VPN/TUN 同时抢默认路由时，只停用已确认冲突且获准调整的那一端，恢复后验证；不清空系统路由表。

## 5. Claude Code、网站和 Desktop

1. Code 若使用本机 HTTP 混合代理，在原有启动方式中为这个进程设置 HTTP_PROXY 和 HTTPS_PROXY；NO_PROXY 只保留真正应直连的本地对象，不能包含目标服务域名。端口从客户端真实设置读取，不猜 7890。
2. 不把代理密码拼进终端参数；需认证时使用客户端支持的受保护设置。已有有意配置的服务网关先识别用途，不擅自改服务地址或删除 API key。
3. 新启动或在自然边界重载 Code，执行一个最小已授权操作，观察实际连接。用户额度/账号响应和网络出口分别判定。
4. 网站使用浏览器访问实际需要的产品；Desktop 使用现有正常安装并完成最小操作。分别在连接面板确认 host、规则命中、Claude-Safe 及最终节点，不拿浏览器代替 Desktop 验收。
5. 登录、验证码或资源域名没有覆盖时，从该次真实请求找到依赖主机，仅将确需同一出口的后缀补进目标规则。不要把所有互联网域名或所有 Cloudflare 流量都强制走目标节点。

## 6. WebRTC 与出口

1. 在需验收的浏览器打开本仓 assets/webrtc-check.html，点击“开始检查”。页面无外部脚本，不上传结果；STUN 检查本身会向页面列出的服务器建立网络请求。
2. 等待最多 8 秒，查看候选类型和地址；host 私网地址或 mDNS 名称不自动等于公网绕行，srflx 公网地址需与预期节点出口比较。没有候选不等于证明无泄漏。
3. 若浏览器暴露非预期公网出口，先检查它是否绕过 TUN/代理和是否走 IPv6，再使用浏览器原生的代理 WebRTC 策略；需要扩展时须有明确安装授权，不随机装指纹扩展。
4. 调整后重跑一次页面，并做一个用户允许的网页通话最小检查；限制 WebRTC 可能破坏通话，不能为了漂亮检测分数损坏业务。
5. IP 检测请求只用来确认这一个请求的出口；必须再配合 Claude 的实际连接链。不同数据库对地区/住宅类型判断不一，不宣称检测站评分等同平台认可。

## 7. 故障拒绝、更新和回滚

1. 保留管理通道，在目标策略只切换本轮节点到不可达测试端点；只在明确有恢复能力时执行。向目标发受控请求，应失败且不能出现 DIRECT 或其他节点。随后立即恢复原端点并验证。
2. 上述只证明“客户端运行但上游失败”的行为，不能证明“整个客户端退出后”仍拒绝直连。需要后一种保证时，必须有系统级目标出站拦截或独立恢复机制；未实现就明确该边界未通过，不冒称全机 kill switch。
3. 执行一次已有客户端正常订阅更新/配置重渲染，再确认节点、组、规则优先级、DNS策略和实际目标连接仍保持。不要关闭所有更新来保住配置。
4. 回滚先恢复本轮持久覆写和原选中条目，再重载客户端；文件恢复后再查运行链。只回收本轮临时探针和输出，现行配置及有效密钥保留。

## 8. 手机 VPN 与原生 WireGuard

1. 用户明确允许整机隧道时，使用生成的 client.conf；该配置将 IPv4/IPv6 默认路由交给隧道，当前服务器只转发 IPv4，IPv6 预期不可用，必须实测而非假定不会绕行。需要正常 IPv6 时另行设计受支持的双栈链路，不能擅自开启绕行。
2. 手机在正式应用商店安装 WireGuard，在 App 中选择“从文件导入隧道”；通过本人控制的加密设备传送导入 client.conf，不上传公共网盘、不在聊天贴二维码。
3. 导入前核对这份配置的 peer 是本设备专属，服务器已经登记对应公钥和 /32。多设备不能复制同一份配置抢占一个 peer；新增设备需增加独立地址和服务器 peer，再定向验证，不覆盖现有 peer。
4. 接受系统 VPN 授权并开启隧道；查看握手和传输量，然后在手机实际 Claude 客户端发起最小操作，核对出口和 DNS。配置出现列表中不等于已经启用。
5. 验收 Wi-Fi 与移动网络各一次，切换网络后允许一次重新握手。测试将产生实际流量，遵守本人套餐预算。无 UDP 条件时保留原配置并使用既有获准兼容线路，不能称原生 WireGuard 保证可用。
6. Android 支持时可在该 VPN 的系统设置中启用“始终开启”和“阻止无 VPN 的连接”；这影响整机，必须是本人所需的范围。iOS 的按需连接不等于所有系统情形都具备企业级 Always-On 或 kill switch，未验证的退出场景明确列出。
7. 配置成功后删除传送中间副本和临时导出，保留客户端有效配置和本人受保护恢复副本。不得为了清理删除另一台设备的现行密钥。
